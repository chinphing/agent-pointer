# Rules：给智能体的长期约束

[English](../../en/user/rules.md) | 简体中文

「Rules」在 Pointer 里不是一样东西，而是**三种**。它们写在哪、注入到提示词的哪一段、对谁生效都不一样 —— 混在一起理解就会觉得「我明明写了规则，怎么没生效」。

```
写在哪                          注入到哪                      谁生效
─────────────────────────────────────────────────────────────────────────
设置 → 智能体 → 个性化    →     [USER RULES]（系统提示）   →   只主 Agent
工作区里的 AGENTS.md      →     # Project Context（系统提示）→   主 + 子 Agent
插件包的 [rules] 目录      →     【插件规则：…】（一条用户消息）→   主 + 子 Agent
```

## 三种 Rules 对照

| | 用户编码规则 | `AGENTS.md` | 插件 `[rules]` |
| --- | --- | --- | --- |
| **写在哪** | 设置 → 智能体 → 个性化 | 工作区里的 `AGENTS.md` 文件 | 插件包里的规则目录 |
| **注入为** | 系统提示里的 `[USER RULES]` 段 | 系统提示里的 `# Project Context` 段 | 一条追加在历史之后的用户消息 |
| **谁生效** | **只主 Agent** | 主 Agent + 子 Agent | 主 Agent + 子 Agent |
| **长度上限** | 4000 字（超出截断） | 无 | 无 |
| **适合** | 全局风格与范围约束 | 项目 / 目录级约定 | 随插件一起分发的规则 |

## 用户编码规则

**设置 → 智能体 → 个性化**，一段自由文本，**最多 4000 字**（按字符计），留空则只用产品默认规则。

它适合写**长期约束**，例如：

- 只改用户明确要求的行为，不顺手重构
- 歧义时先说明假设，不要扩大修复范围
- 相关但未要求的内容放到可选后续，不要一并提交

（上面这三条就是输入框自带的示例。）

写入的这段会以 `[USER RULES]` 为标题进入系统提示，**每一轮都带**。

> **只有主 Agent 会看到它。** 子 Agent（`run_subagent` 派出去的 worker）的提示词里**不包含** `[USER RULES]`。想让子 Agent 也遵守同样的约束，写进 `AGENTS.md`（见下）。

超过 4000 字时**不会报错**，而是截断，并在末尾追加 `…(truncated at 4000 chars)`。所以「写了没生效」有时其实是「被截掉了」。

## AGENTS.md

`AGENTS.md` 是**文件**，放在工作区里，随仓库走 —— 适合写「这个项目怎么干活」。

### 会加载哪些

只有两类：

| 位置 | 作用范围 |
| --- | --- |
| `~/.pointer/AGENTS.md` | 全局，对你所有工作区生效 |
| 从 **git 根**沿路径逐层向下到**工作区**的 `AGENTS.md` | 该目录及其下级 |

```
~/…/.pointer/AGENTS.md                     ← 全局，总是先加载
repo/AGENTS.md                             ← git 根
repo/packages/AGENTS.md                    ← 中间层
repo/packages/web/AGENTS.md                ← 工作区（当前会话绑定的目录）
```

上例中工作区是 `repo/packages/web` 时，这四份都会被加载；同级的 `repo/packages/api/AGENTS.md` **不会**被加载 —— 不扫旁支。

### 逐层是怎么算的

1. 从工作区**向上**找 `.git`，得到 git 根（最多向上 64 层）
2. 从 git 根**向下**走到工作区，**两端都算**，每层最多取一份
3. 找不到 git 根时，只读工作区根目录那一份
4. 工作区就是文件系统根（`/`、`C:\`）时不读项目层

每份文件在提示词里带上自己的标签，就是它相对 git 根的路径：`AGENTS.md`、`packages/AGENTS.md`、`packages/web/AGENTS.md`。

### 注意

- 文件名**只能是 `AGENTS.md`**，大小写敏感，没有别的命名变体
- **没有** `.agents/` 目录约定，也没有 `.agents/AGENTS.md`；放在 `.agents/` 里不会生效
- `AGENTS.md` 同时进主 Agent 与子 Agent 的提示词，所以「子 Agent 也要遵守」的规则写这里

## 插件 `[rules]`

插件可以在自己的清单里声明一个规则目录：

```toml
[rules]
path = "rules/"
```

启用该插件后，目录下的 `*.md` / `*.mdc` 会在每一轮被拼成一条**用户消息**追加在对话历史之后，开头是：

```
【插件规则：{插件名}（{插件 ID}）】
```

因为是用户消息而不是系统提示，它的位置在历史之后（越靠近请求末尾，模型的注意力越强）。

插件规则**不能单独编辑**：它随插件分发，改插件或停用插件才会变。

## 优先级与叠加

三种 Rules 是**叠加**的，代码里**没有覆盖、也没有去重** —— 都拼进同一份提示，冲突要靠你自己避免。

系统提示里的拼接顺序（主 Agent 轮）：

```
角色提示词 → 界面语言规则 → 工具说明 → [Environment]
  → 记忆 / 用户画像 → [USER RULES] → # Project Context
```

官方给 Agent 的优先级栈（写在内置的沟通规范里）是：

```
对话内容 → [SESSION SCOPE] → [USER RULES] → Project Context
  → Agent profile → 可选后续
```

注意两点：

- 插件 `[rules]` **不在**这张栈里 —— 它以用户消息形式出现，位置在历史之后
- 越靠后的内容在提示里越「近」，但栈本身说明的是**语义优先级**：`[USER RULES]` 高于 `# Project Context`

写规则时的实用建议：

| 想要 | 写哪 |
| --- | --- |
| 全局的风格 / 范围约束 | 用户编码规则 |
| 某个项目的约定（含子 Agent） | 该项目的 `AGENTS.md` |
| 跟着插件走的规则 | 插件的 `[rules]` |
| 一次性、只对这次任务的要求 | 直接说在对话里，或用 `[SESSION SCOPE]` |

## 常见问题

**写了用户规则但子 Agent 不遵守**

这是设计如此：`[USER RULES]` **只注入主 Agent 轮**。需要子 Agent 也遵守的规则，写进 `AGENTS.md`。

**规则「写了没生效」**

按顺序排查：

1. 输入框是否为空（留空 = 只用产品默认规则）
2. 是否超过 4000 字被截断 —— 被截掉的部分不会进提示
3. 是否指望子 Agent 遵守（见上）
4. 如果是 `AGENTS.md`：文件是否在工作区路径上，或是否放在 `.agents/` 里（那里不生效）

**`AGENTS.md` 放在 `.agents/AGENTS.md` 没反应**

Pointer 不读 `.agents/` 目录。放到工作区（或 git 根到工作区之间的某一层）的 `AGENTS.md` 才行。

**两份规则互相矛盾**

代码不做冲突消解，两份都会进提示。请把它们改成不冲突的表述，或把项目级例外写进 `AGENTS.md`（它比用户规则更「贴近」当前项目）。

**改了 `AGENTS.md` 要重启吗**

不用。每轮都会重新读取工作区里的文件。
