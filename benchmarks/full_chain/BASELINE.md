# full_chain 基线

数据：`pointer-eval-data/full_chain/`，**一个目录 = 一个数据集**，用
`POINTER_E2E_SPLIT` 选：

| 目录 | 条数 | 内容 |
|---|---|---|
| `sudoku/` | **104** | 数独游戏界面（棋盘格 54 + 底部键盘 50） |
| `screenspot/` | **300** | ScreenSpot-Pro 专业软件 4K（hint 基线 56.7 %，见 2026-11-05 一节） |
| 不设 / `all` | 404 | 全部合并 |

```bash
# 数独 104 条（历史基线的口径）
POINTER_E2E_SPLIT=sudoku POINTER_E2E_MODE=hint  POINTER_E2E_CONCURRENCY=8 cargo test --release -p pointer-core --test full_chain full_chain_grounding -- --ignored --nocapture
POINTER_E2E_SPLIT=sudoku POINTER_E2E_MODE=agent POINTER_E2E_CONCURRENCY=8 cargo test --release -p pointer-core --test full_chain full_chain_grounding -- --ignored --nocapture

# 全部 404 条
POINTER_E2E_SPLIT=all POINTER_E2E_MODE=hint POINTER_E2E_CONCURRENCY=8 cargo test --release -p pointer-core --test full_chain full_chain_grounding -- --ignored --nocapture
```

> **测试文件改过名**：`tests/computer_e2e/` → `tests/full_chain/`，测试函数
> `computer_e2e_grounding` → `full_chain_grounding`。旧文档里的 `--test computer_e2e`
> 会报「no test target named」。`POINTER_E2E_MODE` 支持 `none | oracle | agent | hint`。
>
> **2026-11-01 数据集重组**：原 `general/`(50) 与 `sudoku/`(54) 合并为 `sudoku/`(104)，
> 两者都是数独游戏界面（前者目标是底部数字键盘，后者是棋盘格子）。旧的
> `POINTER_E2E_SCOPE=full` 当时等于 104 条，现在等于 404 条——**旧命令跑出来的数字
> 与新命令不可比**，一律改用 `POINTER_E2E_SPLIT`。

## 2026-11-01 — communication.md 四类目标 + 容差圈（三次均值）

**改动**：`prompts/communication.md` 的 `## Positioning` 从两类（Large/Small）
扩到四类（Area / Point / Line / Gap-blank），`Control type` 增六个值
（`divider / separator / progress bar / insertion point / gap / blank area`）。
同时含上一轮的「索引降级 + 容差圈」两项，**三者混在一起，无法分离归因**
（已决定不做 A/B）。

**口径差异——读数字前必须知道：**

| | 基线 86.5 % | 本次 90.7 % |
|---|---|---|
| 采样 | **单遍** | **三次均值** |
| 数据 | 104 条 | 104 条（合并后同名） |
| 命令 | `SCOPE=full` | `SPLIT=sudoku` |

**三次原始数字：**

| 次 | 命中 | 命中率 | hint 耗时 |
|---|---|---|---|
| 1 | 91/104 | 87.5 % | 9.3 s |
| 2 | 96/104 | **92.3 %** | 12.6 s |
| 3 | 96/104 | **92.3 %** | 8.1 s |
| **均值** | 94.3/104 | **90.7 %** | — |

| | 值 |
|---|---|
| 与基线差 | **+4.2 pp** |
| 三次极差 | **4.8 pp**（87.5 → 92.3） |
| 单遍标准误 | 3.1 pp |
| 三次均值标准误 | 1.8 pp |
| 差值显著性 | **2.3 σ** |

**结论：三次全部 ≥ 基线（最低 87.5 % > 86.5 %），方向为正。**

但 +4.2 pp **不宜当作精确提升量**，因为：

1. 基线是单遍（±3.1 pp 波动），本次是三次均值（天然更靠近真值），口径不公平；
2. 历史波动范围是 **86.5–91.3**，本次均值 90.7 % 落在**这个范围的上沿**，
   无法排除「落在历史高值区」；
3. 归因不可分离（三个改动同时生效）。

**按尺寸（三次均值）：**

| 尺寸 | n | 命中率 |
|---|---|---|
| 小 (<40px) | 1 | — |
| 中 (40–120px) | 101 | 92.8 % |
| 大 (>120px) | 2 | 100 % |

104 条里 101 条是 40–120px，尺寸分桶在这个数据集上区分度很低。

**耗时**：hint 8.1–12.6 s / 例，locate 0.0 s（hint 模式不进定位层）。

### 顺带发现的真问题（未修）

`f91c8a52`（7 键）首次跑到 538px 偏差。推理原文：

> "the keys span from about x=85 to x=440 in the image. The **"7" key** ... is at
> approximately **x=895**"

**模型自己说键盘范围是 85–440，却给出 x=895**——在键盘外面。这是主 LLM 在
「1000 归一化网格 ↔ 像素」换算时会自相矛盾，属于提示词层面的问题，不是数据问题。

重测一遍旧版本，否则分不清是代码还是模型。

## 2026-10-30 — 真值框按「描述行列 + 9×9 格阵」重算（历史基线）

**先修数据，再看模型。** `e2e_truth.json` 的 `bbox` 原本来自 `export_e2e_dataset.py`
的 `outcome.box`——是 pipeline 自己点出来的框，不是人工标注。校验发现它的中心
相对真实格子中心有 9.6px 标准差，最大偏 24px（一格 41px），**超过了半格，
足以让「点中了」被判成「没点中」**。

**前三版重算都错了，错因值得记下来：**

| 版本 | 方法 | 结果 |
|---|---|---|
| v1 | 逐条检测网格线 | 数字笔画被当成网格线，出现 122×6 的「格子」 |
| v2 | 全局拟合检测到的线 | 相位被噪声拖偏一整格（G5 算成 G6） |
| v3 | 吸附旧 bbox 中心到格阵 | 旧框误差 24px > 半格 20px，吸附到隔壁格 |

**v4 才正确**：把所有 51 条数独目标的旧框中心投影到 1D，拟合出 9 个格子带的中心
（x step 39.98、y step 41.00），然后**从描述里正则解析「G行第五列」，直接查格阵**——
完全不看旧框，所以旧框的误差不会传导。

交叉验证：`d6373a20` 算出 G5 中心 (276, 509)，而 locate 当时收到的 hint 中心是
(280, 506.5)，差 3.5px。**说明那条 case 里主 LLM 的 hint 本来是对的，是旧真值
框偏了 24px 才判它失败。**

**未重算的 53 条**是键盘按键、按钮、图标——不是网格结构，真值框就是元素边界。

| | hint | agent | 差距 |
|---|---|---|---|
| **新真值（单遍）** | **86.5 %** | **95.2 %** | **8.7 pp** |
| 旧真值（各 2–3 遍） | 85.6 % | 95.5 % | 9.9 pp |

**修真值前后整体数字几乎不变（86.5 vs 85.6、95.2 vs 95.5）**——因为 51 条修正里
大部分落点本来就在正确格子附近，只是个别 case 的判定翻转了。

**轮次与耗时（每样本均值）：**

| 模式 | rounds_avg | hint | locate |
|---|---|---|---|
| hint | 0.00 | 7.7 s | 0.0 s |
| agent | 1.14 | 7.8 s | 8.9 s |

**分档（agent）**：小(<40px) 1/1、中(40-120px) 96/101 = 95.0%、大(>120px) 2/2。

单遍标准误约 3 pp，8.7 pp 的差距需要多遍确认。

## 2026-10-30 — 按检测网格重算（作废）

以下是错误版本，保留用于说明错因：

**先修数据，再看模型。** `e2e_truth.json` 的 `bbox` 原本来自 `export_e2e_dataset.py`
的 `outcome.box`——是 pipeline 自己点出来的框，不是人工标注。校验发现它的中心
相对真实格子中心有 9.6px 标准差，31% 的样本偏超过 10px（一格 41px）。

**重算方法**：收集所有数独格子的检测网格线，拟合一套全局 9×9 格阵
（纵向 origin 16.95 step 39.58，横向 origin 238.87 step 41.17），把每个格子目标
吸附到它所在的格。重算后 51 条的尺寸是 39.6×41.2，零方差。

**未重算的 53 条**是键盘按键、按钮、图标——它们不是网格结构，真值框就是元素
边界，保留原值。

| | hint | agent | 差距 |
|---|---|---|---|
| **新真值（各三遍）** | **90.4 %** | **94.2 %** | **3.8 pp** |
| 旧真值（各 2–3 遍） | 85.6 % | 95.5 % | 9.9 pp |

明细：

| 遍 | hint | agent |
|---|---|---|
| 1 | 94/104 = 90.4 % | 96/104 = 92.3 % |
| 2 | 95/104 = 91.3 % | 100/104 = 96.2 % |
| 3 | 93/104 = 89.4 % | 98/104 = 94.2 % |
| 均值 | **94/104 = 90.4 %** | **98/104 = 94.2 %** |

**轮次与耗时（每样本均值）：**

| 模式 | rounds_avg | hint | locate |
|---|---|---|---|
| hint | 0.00 | 7.6–8.7 s | 0.0 s |
| agent | 1.10–1.15 | 8.7–11.6 s | 8.8–9.9 s |

`hint` 模式 `rounds_avg=0` 是因为它只给主 LLM 的框打分，不进 locate。

### 旧真值把 agent 压低了

同一套代码，换真值后 **hint +4.8 pp，agent −1.3 pp**。

旧框偏的是随机方向（均值 −1.3px、标准差 9.6px），而 agent 的落点被 locate
修正过、更靠近真实格子中心——**落点越准，越容易落在旧框外面**。所以旧真值对
agent 的惩罚比 hint 重，把两者的差距从真实的 3.8 pp 拉成了 9.9 pp。

**结论：之前「agent 比 hint 高 9.9 pp」这个数字有一半是真值框的偏差造成的，不是
verify 的功劳。** 真实差距是 3.8 pp。

## 2026-10-29 晚 — locate 与 verify 两处修复之后（旧真值）

| | hint | agent | 差距 |
|---|---|---|---|
| 修复前（各三遍均值） | 88.1 % | 90.4 % | 2.3 pp |
| **修复后（各 2–3 遍均值）** | **85.6 %** | **95.5 %** | **9.9 pp** |

明细：

| 遍 | hint | agent |
|---|---|---|
| 1 | 87/104 = 83.7 % | 100/104 = 96.2 % |
| 2 | 91/104 = 87.5 % | 98/104 = 94.2 % |
| 3 | — | 100/104 = 96.2 % |

**agent +5.1 pp，hint −2.5 pp。** agent 的 100/104 是历史最高（此前最好 97/104）。

### 改了什么

两处，都在 locate 层：

1. **`stay_local` 判据**：原来只要 verifier 的 `center` 不是 `Unclear` 就留在当前
   crop 里重找。但 `position = no`（「框里这个不是描述指定的那一个」）说明 crop
   本身就开错了地方，在错的窗口里重找只能再找到一个同类元素。现在
   `position = no` 直接换全屏。

2. **`center` 判据改成算比例**：`verify_body.md` 早就要求「先找四条边界线」，
   但没给可数标准，于是偏 25 px（半格）的框被判 `center.ok = yes`。现在要求算出
   红点中心在目标格内的百分比：30–70 % 才判 yes，15–30 % / 70–85 % 判 no。

### 为什么 hint 反而降了

`hint` 模式是**主 LLM 的框直接计分**，`rounds_med=0`——verify 根本不参与。判据
变严对它没有任何帮助，那 −2.5 pp 落在它自己的波动范围里（历史 86.5–91.3）。

**两模式的差距从 2.3 pp 拉到 9.9 pp，这才是 verify 起作用的形状**：agent 走
locate + verify，判严了能靠 re-locate 纠回来；hint 模式没有纠正机会。

### 噪声提醒

`hint` 三遍极差 5.7 pp、`agent` 三遍极差 1.9 pp（修复前）。单遍标准误按
p≈0.9、n=104 算约 3 pp。**小于 6 pp 的差异需要多遍才能判断。**

## agent 模式相对 hint 没有可分辨的提升

两模式差 **2.3 条 / 2.2 pp**。单遍标准误按 p≈0.89、n=104 算是 3.1 pp，三次均值
1.8 pp；两模式差值的标准误约 2.5 pp，**t ≈ 0.9**。这个差距在噪声里。

这正是后面要解决的问题：agent 模式加载了完整的角色提示词（23192 字符）、走了
verify 回路、多花了 4.4 倍时间，命中率却和「主 LLM 直接产框」持平。

尺寸分桶上两者反向：agent 在小目标上**低 8.8 pp**、在中目标上**高 4.2 pp**。小桶
只有 15 例，单例 6.7 pp，这 8.8 pp 就是 1–2 例的差别，不足以下结论。

## 逐条稳定性

hint 三遍的命中次数分布：

| 命中遍数 | 条数 |
|---|---|
| 3/3 | 78 |
| 2/3 | 18 |
| 1/3 | 5 |
| 0/3 | 3 |

**75 % 的用例三遍全中**，翻转集中在 23 条（22 %）。agent 模式不打印逐条结果
（只有汇总），所以同样的分布目前只能从 `computer-captures/locate/*.json` 的 trace
反推——那是后续要做的事，不在这份基线里。

## 3 条稳定失败

三遍全错的都是数独盘面的**空单元格**，且落点**全部偏左**：

| scene | 描述 | 三遍落点偏移 |
|---|---|---|
| `07f72a66` | B8 空单元格 | −27 / −24 / −31 px |
| `0dfd3f6f` | A6 空单元格 | −55 / −40 / −26 px |
| `d6373a20` | G5 空单元格 | −25 / −21 / −28 px |

一格宽约 41 px，所以这不是「瞄不准」，而是**框到了左邻格**。三条描述都是
「在带数字 X 的 Y 格右侧」这种以邻格定位的写法，模型把「右侧」理解成了「这个格子
的右半部分」而不是「右边那一格」。

这是**描述歧义**，不是定位能力问题。要修得从描述写法或真值口径入手，不属于
verify 的范围——但它说明这 3 条在基线里是**恒定失分项**，比较任何改动时都要把
它们当成常数项看。

## 与旧数字的关系

2026-10-28 的记录是 **81.3 %（87/107，hint 模式）**，不能直接比：

- 删掉了 3 条垃圾数据（描述是「Dock 中央空白处」）
- 修正了 7 条真值框（`e2e_truth.json` 的 `bbox` 原本来自 pipeline 自己的输出，
  不是人工标注；用网格拟合 `x0=112.8, cw=41.24, y0=260.6, ch=41.31` 重算）
- 107 → 104 条

旧口径下同一批修好的数据是 90/104 = 86.5 %，与本次 hint 的 88.1 % 同一量级，
差异来自模型侧波动（本次三遍极差就有 5 条）。
