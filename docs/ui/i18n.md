# UI internationalization (zh-CN / en)

## Goal

Every user-visible string follows the UI language preference.
Desktop and Web share `src/`; one Vue migration covers both.

## Never translate

- Product name: **Pointer**
- Model / channel brands (千问, 飞书, …)
- Technical identifiers (API Key, MCP, agent ids, tool names as wire ids)

## Preference

| Field | Values | Default |
| --- | --- | --- |
| `UserSettings.uiLocale` | `"system"` \| `"zh-CN"` \| `"en"` | `"system"` |

- **system**: `navigator.language` / OS locale — if it starts with `zh`, use Chinese; otherwise English.
- Persisted in `user_settings.json` (desktop + Web).
- Cached in `localStorage` key `pointer-ui-locale` for bootstrap before settings load.
- Changing language applies **immediately** (no restart).

Resolve helpers: `src/lib/uiLocale.ts` (`resolveUiLocale`, `applyUiLocale`).

## Vue stack

| Piece | Location |
| --- | --- |
| Library | `vue-i18n` Composition API, `legacy: false` |
| Instance | `src/i18n/index.ts` — mounted in `src/main.ts` |
| Catalogs | `src/locales/zh-CN.json`, `src/locales/en.json` |
| Templates | `$t('key')` / `t('key')` |
| Script / stores | `import { t } from '@/i18n'` (same instance) |

### Key naming

- Dot-separated English: `chat.composer.placeholder`
- Group by surface: `common.*`, `shell.*`, `chat.*`, `settings.*`, `agent.*`, `tools.*`
- **Do not** use Chinese as keys

### Interpolation

- Placeholders: `{name}` — e.g. `$t('tools.groupExploreFiles', { n: 3 })`
- Dates / numbers: `Intl` APIs

### New UI rule

Every new user-visible string must go through `t()` / `$t()`.
Do not hardcode Chinese (or English-only) copy in `src/components`.

## Settings UI

Language control lives under **系统设置 → 界面显示** (`GenerationSettingsPanel`):
跟随系统 / 中文 / English.

Optional later: quick switch next to theme in `AccountMenu`.

## Rust (P4+)

Runtime catalogs in `pointer-core` (`i18n` module):

- Stable message **keys** + embedded `zh-CN` / `en` tables
- Resolve locale from the same `uiLocale` preference
- Emit **already-rendered** strings on IPC / stream events (tool labels, agent UI names, `UiToast`, command errors)
- Do not hardcode user-visible Chinese in Rust UI paths

## Agent / model side (P5)

- Keep system prompts as English instructions to the model when that is the product choice
- If the assistant should reply in the UI language, inject a short rule
  (`Reply in the user's UI language`) rather than maintaining bilingual prompt books
- Skills / experience cards may ship their own language; that does not block code i18n

P5 iterates by product need and does not block earlier releases.

### P5 reply language

`env_prompt` injects a short English instruction into `[Environment]`:

> Reply language: Reply to the user in **Chinese (Simplified)** / **English** …

Resolved from `UserSettings.uiLocale` (`system` follows OS `LANG`).
System prompts stay English; only this rule steers the assistant’s reply language.

### Key parity

`src/locales/localeParity.test.ts` asserts zh-CN / en key sets match.

### Rust catalogs

`pointer-core::i18n` — `resolve_ui_locale` / `t` / `tf` with embedded zh-CN / en tables.
Used by `tools/display`, `agent_ui` composer labels, and context/sub-agent UiToasts.

## Packaging note

Installer language (NSIS / DMG) and `tauri.conf.json` `language` are packaging concerns — tracked separately; they do not block in-app i18n.
