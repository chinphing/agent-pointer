# Webhook API

English | [简体中文](../../zh-CN/developer/webhook-api.md)

Trigger Pointer Agent over HTTP (CI, GitHub, custom systems, …). **Only Pointer server** exposes the inbound endpoint; you must first deploy `pointer-server` and expose a public address.

> For IM platform callbacks (Feishu/DingTalk/WeCom HTTP inbound) see [channel-integration.md](channel-integration.md) — that is a different API.

## Quick start

1. In Pointer **Settings → Automation**, add a source (e.g. `ci`) and copy the **Token** and the full URL.
2. Send a request to `POST https://<host>/api/webhooks/<src>` with the Token in a header.
3. The default is **202** asynchronous execution; set `blocking: true` when you need the result synchronously.

## Authentication

| Item | Description |
|----|------|
| URL | `POST /api/webhooks/:src` |
| `:src` | Source id (starts with a letter/digit, only `-`, `_`), and must match what is configured in the automation panel |
| Token | Generated by the panel; one of two request headers: `Authorization: Bearer <token>` or `X-Pointer-Token: <token>` |
| Custom header | The panel can assign a dedicated Header name to a source (e.g. `X-My-Token`); in that case only the raw value of that header is accepted |

Do not pass the Token in the query string. Authentication failure → **401**.

## Settings API (managing tokens)

The automation panel manages sources through the following endpoints (requires **account login**, unlike the Bearer auth of the Webhook inbound):

| Method | Path | Description |
|------|------|------|
| GET | `/api/webhooks/config` | List configured sources (trailing-digits preview only, never the full Token) |
| POST | `/api/webhooks/config` | Add a source Token (first write only); optional `sessionMode` |
| PATCH | `/api/webhooks/config/:src` | Update source settings (e.g. `sessionMode`) |
| GET | `/api/webhooks/config/:src/token` | Reveal the full Token (for copying from the settings page) |
| DELETE | `/api/webhooks/config/:src` | Delete the source Token |
| DELETE | `/api/webhooks/config/legacy` | Clear the legacy global Token |

**Reveal response example**:

```json
{
  "src": "ci",
  "token": "abc123…",
  "preview": "****1234"
}
```

## Triggering the Agent

### Request body

**Message fields** (at least one; when none is present the [native payload fallback](#native-payload-fallback) applies):

| Field | Description |
|------|------|
| `text` | Text sent to the Agent |
| `message` | Same as `text` (compatibility alias) |
| `messages` | Message array; a single `user` entry is appended to the current day's conversation; with `assistant`/`tool` or multiple entries it is treated as the full history |

Append (a single `user`, or `text` / `message`) submits only that one sentence.
The server writes it into the current day's conversation, then starts a run against the working set — it does not read the whole stored history into this request.
Full history uses the `messages` in the request directly, without reading the store first.

**Optional control fields**:

| Field | Default | Description |
|------|------|------|
| `name` | none | Prefixes this turn's message with `[name] …` |
| `conversationId` | automatic | Normally omit; by default the conversation continues per source + local day boundary |
| `agentMode` | instance default | e.g. `single` |
| `leadAgentId` | instance default | e.g. `general`, `coder` |
| `idempotencyKey` | none | Idempotency key; a repeated request returns the same `runId` and does not execute again |
| `enabledSkillIds` | `[]` | List of Skill ids enabled for this request |
| `workspaceRoot` | empty | Absolute workspace path; when empty the session default is used |
| `blocking` | `false` | When `true`, wait synchronously for the Agent to finish |
| `timeoutSeconds` | `120` | Longest wait in seconds when `blocking`, up to 600 |
| `attachments` | none | Attachment list, see [Attachments](#attachments) |
| `deliver` | none | Run → IM delivery spec (e.g. `feishu`, `feishu:ou_xxx`, `feishu:group:oc_xxx`, `all`); after the run finishes the final reply is pushed to the matching channel. Format in [channel-integration.md](channel-integration.md) |

The whole JSON body is capped at **256 KiB**. Empty body → **422**; invalid JSON → **400**; over the limit → **413**.

### Native payload fallback

When `text` / `message` / `messages` are not provided (or are all empty):

- **JSON body** → the entire compact JSON becomes the user message (prefixed with `[src]`, e.g. `[github] {"ref":…}`)
- **Plain-text body** → the raw text becomes the user message

Suited to GitHub, Codeup and similar services that POST their native webhook body directly, with no reformatting.

### Response

| Mode | HTTP | Response body |
|------|------|--------|
| Async (default) | **202** | `{ "runId": "…", "status": "accepted" }` |
| Async polling | **GET** `/api/webhooks/:src/runs/:runId` | `{ "runId", "status", "conversationId", "text?", "error?" }` |
| Sync `blocking: true` | **200** | `{ "ok": true, "runId": "…", "conversationId": "…", "text": "…" }` |
| Sync failure | **500** | Error message |
| Sync timeout | **504** | Exceeded `timeoutSeconds` |

On an idempotency hit the async path still returns **202**, and `status` may be `reused`.

### Async polling result

The default **202** only means the run has been enqueued. Poll with the same source Token:

```http
GET /api/webhooks/:src/runs/:runId
Authorization: Bearer <token>
```

| `status` | Description |
|----------|------|
| `queued` / `running` | Still executing; `text` / `error` are empty |
| `finished` | Done; `text` is the Agent's final reply |
| `failed` / `cancelled` | Terminated; `error` carries the reason |

Poll every 1–3 seconds until `status` reaches a terminal state.

### Conversation continuation

When `conversationId` is not passed, conversation grouping is decided by the source's **`sessionMode`** (configurable in the automation panel):

| Mode | Description |
|------|------|
| `per_delivery` (default) | One independent conversation per delivery; the delivery id comes from `idempotencyKey` → `X-GitHub-Delivery` / `Svix-Id` / `X-Request-ID` → generated automatically |
| `daily` | The same `:src` shares context within one **local calendar day** (rolls over at 04:00) |

Under `per_delivery` it is recommended to write the GitHub `delivery` id into `idempotencyKey`, so retries do not open a new conversation.

## Attachments

For large files, **upload first, then reference**; do not stuff large files into JSON.

| Step | Method | Path | Limit |
|------|------|------|------|
| Upload | POST | `/api/webhooks/:src/upload` | **30 MiB** (multipart) |
| Trigger | POST | `/api/webhooks/:src` | JSON referencing `storageRelPath` |

**Upload** — `multipart/form-data`:

| Field | Required | Description |
|------|------|------|
| `file` | yes | File content |
| `fileName` | no | File name (may also be taken from the part filename) |
| `mimeType` | no | MIME type |
| `conversationId` | no | May be specified when it matches the conversation id; defaults to the current day's webhook conversation |

Authentication is the same as the trigger endpoint.

**Upload response example**:

```json
{
  "conversationId": "webhook:ci:20260629",
  "attachmentId": "wh-abc123",
  "storageRelPath": "webhook_ci_20260629/wh-abc123_report.pdf",
  "kind": "document",
  "mimeType": "application/pdf",
  "fileName": "report.pdf",
  "sizeBytes": 12345
}
```

**Referencing at trigger time** — example `attachments` array element:

```json
{
  "id": "wh-abc123",
  "kind": "document",
  "mimeType": "application/pdf",
  "fileName": "report.pdf",
  "storageRelPath": "webhook_ci_20260629/wh-abc123_report.pdf"
}
```

`storageRelPath` must come from the upload response of the same conversation.

### Example (curl)

```bash
TOKEN="<Token from the panel>"
HOST="https://your-pointer-host"

# 1. Upload
curl -X POST "$HOST/api/webhooks/ci/upload" \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@./report.pdf"

# 2. Trigger (fill the fields returned by upload into attachments)
curl -X POST "$HOST/api/webhooks/ci" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Please analyse the attachment",
    "attachments": [{
      "id": "wh-abc123",
      "kind": "document",
      "mimeType": "application/pdf",
      "fileName": "report.pdf",
      "storageRelPath": "webhook_ci_20260629/wh-abc123_report.pdf"
    }]
  }'
```

## GitHub integration example

1. Add the source `github` in the Pointer automation panel and copy the Token.
2. GitHub → Settings → Webhooks → Payload URL: `https://<host>/api/webhooks/github`
3. **Secret**: the same as the Pointer Token; if GitHub only sends an HMAC signature, verify it in a middle layer and then forward with `Authorization: Bearer <token>` added.
4. The JSON of push and similar events has no `message` field → the native payload fallback applies automatically, and the Agent receives `[github] {"ref":"refs/heads/main",…}`.
5. It is recommended to set `idempotencyKey` to the GitHub `delivery` id, so retries do not execute twice.

## Synchronous call example

```bash
# async trigger + polling
RESP=$(curl -s -X POST "$HOST/api/webhooks/ci" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"text":"Summarise this build log"}')
RUN_ID=$(echo "$RESP" | jq -r .runId)
until true; do
  BODY=$(curl -s "$HOST/api/webhooks/ci/runs/$RUN_ID" \
    -H "Authorization: Bearer $TOKEN")
  STATUS=$(echo "$BODY" | jq -r .status)
  case "$STATUS" in finished|failed|cancelled) echo "$BODY" | jq .; break ;; esac
  sleep 2
done
```

```bash
curl -X POST "$HOST/api/webhooks/ci" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Summarise this build log",
    "blocking": true,
    "timeoutSeconds": 300
  }'
```

On success the response `text` is the body of the Agent's final reply.
